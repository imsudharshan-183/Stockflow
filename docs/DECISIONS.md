# Decisions

The algorithm notes, modeling assumptions, and operational security summary live here. For the engine formulas, worked example, and constants table, see [docs/ENGINE.md](ENGINE.md); for numbered Architecture Decision Records (`ADR-001`+), see [docs/ADR.md](ADR.md); for setup and the folder map, see [README.md](../README.md).

## Problem framing

Branch managers and company admins open the action queue each morning to decide which stock moves need attention. Each row is a transfer, a reorder, or a markdown, with a net BHD benefit (`BD`) and a sentence that names the cover, the reorder point, the freight breakdown (for transfers), and the money. The network is 15 branches across Bahrain and about 500 SKUs. History is 120 synthetic days. Managers can inspect the inputs behind an estimate before approving a move.

## StockFlow assistant

The signed-in assistant explains the product and its glossary, then answers business questions through a small set of read-only application lookups. Its base instructions define StockFlow terms and supported work. The model can classify a question or choose a supplied fact to highlight in a brief. The API constructs the displayed explanation, figures, and links from its scoped records. Unsupported requests return guidance.

Role and branch scope come from the authenticated session and server-side permission checks. Admins can ask across active network branches. Managers can ask about assigned branches, including authorized reports and forecasts. Staff receive store-level operational help, inventory, deliveries to receive, and data-entry guidance. Financial and management-only details are excluded for staff. The model cannot run MongoDB queries, mutate records, access credentials, or override API permissions. If a provider is unavailable, supported structured questions use the local lookup path.

## Algorithm

1. **Velocity.** An exponentially weighted average of daily sales. The span is 28 days, so the weight on the latest in-stock day is `2 / 29`. Days with nothing available to sell are left out of the average and out of sigma. A stockout is not evidence that demand disappeared.
2. **Safety stock.** `z * sigma * sqrt(lead time)` with `z = 1.65`. The reorder point is `velocity * lead time + safety stock`.
3. **Classification.** Cover is on hand divided by velocity. Above 60 days is overstock. Below the reorder point is at risk. Overstock wins if both could apply. No in-stock history means the SKU is new and gets no action. Zero velocity with stock on hand is unlimited cover, not a division by zero.
4. **Matching.** For each SKU, donors can give units above 30 days of cover plus safety stock. Receivers need units to reach 14 days of cover. The greedy pass takes the pair with the highest net benefit, moves the stock, and repeats. Ties break toward the lower branch index so the order does not flicker.
5. **Net benefit.** `lost margin avoided + carrying cost saved - transfer cost`. Lost margin is the margin on units that would be missed over the lead time, capped by the quantity moved. Carrying cost uses a 20% annual rate and the donor's excess cover, capped at a year. Transfer freight uses `TotalTransferCost(Q, D) = BD 1.500 + (BD 0.150 × D_km) + (BD 0.250 × Q)` via Haversine distance across Bahrain's 2–45 km network. If one more unit saves less holding cost than the marginal `BD 0.250` per-unit handling fee, the quantity stops at the lost-sales units. Transfers under 5 units, or with a net benefit of 0 or less, are skipped.
6. **Fallbacks.** A receiver that is still short is a reorder up to the greater of the 14-day target and the reorder point. If the SKU has overstock and nobody is short, the surplus is a markdown at 30% off. The benefit compares clearing now with the full-price margin that would have been earned over the hold window, plus the holding cost avoided.
7. **Ranking.** Sort by net benefit, then SKU, branch, and action. The materiality screen (`netBenefit >= BD 9.500` and `quantity >= 5` in `isMaterialRecommendation`) is applied in the API service after this ranking, so the engine's golden quantities and backtest moves stay put.

## Why this, not ML or linear programming

A learned demand model and a network LP would both need more history than 120 days, and neither would show its work in one sentence. This version is explainable, deterministic, and covered by a worked example (60 units from branch B to branch A). Pairing inside one SKU is a small loop. Across SKUs the work is independent, so the shape is closer to O(n log n) ranking of the resulting actions than to a single giant program. A solver can replace `greedyMatcher` later without rewriting classification. A forecaster can replace `ewmaForecaster` the same way.

## Assumptions

- Lead time belongs to the product, from 1 to 21 days, not to the lane between branches.
- Service level `z = 1.65`.
- Annual holding cost is 20% of unit cost.
- Markdowns take 30% off the shelf price.
- Transfer freight is `BD 1.500` fixed + `BD 0.150/km` Haversine distance + `BD 0.250/unit` handling (`TotalTransferCost(Q, D)`). Engine planning does not round to case packs, enforce truck volume limits, or model expiry dates; instead, managers may override approved quantities at commit within server-enforced bounds using `CASE_PACK`, `TRUCK_CAPACITY`, `PROMO_HOLD`, or `OTHER` reason codes.
- Transfers are available the same morning. Reorders arrive after the lead time.
- Branches do not compete for the same inbound truck.
- Demand during the lead time is treated as roughly normal and independent across branches.
- Prices are tiered in native BHD (`0.500–4.000` Low, `2.000–15.000` Mid, `15.000–120.000` High) using non-round market decimals. Unit cost is 55% to 75% of price.
- The backtest still delivers the receipts implied by history, then adds StockFlow's moves on top. It does not cancel purchase orders the old process already sent.
- **Seed dataset stocking profile (`packages/core/src/seed/generate.ts`)**: Healthy branch-SKU replenishment targets are calibrated above an analytical EWMA reorder bound (`expectedRop = mean * leadTimeDays + 2.1 * sqrt(max(0.05, mean) * leadTimeDays)`, accounting for each SKU's staggered `7–21` day cycle depletion while capping below the `60`-day overstock band), with deterministic under-stocking across three realistic store tiers:
  - **Before tuning** (uniform `mean * 20` refill across `7–21` day cycles): `41.88%` network `AT_RISK` (`3,141 / 7,500`), `4.56%` `OVERSTOCK` (`342`), `1.61%` dead stock (`121`); per-branch `AT_RISK` ranged from `36.6%` (`BR-010`) to `48.4%` (`BR-005`).
  - **After tuning**: `12.29%` network `AT_RISK` (`922 / 7,500`, inside `8%–15%`), `7.61%` `OVERSTOCK` (`571`), `1.71%` dead stock (`128`); three hotspot branches in `20%–30%` (`BR-004: 26.0%`, `BR-005: 26.0%`, `BR-009: 25.8%`), three low-risk branches in `2%–5%` (`BR-003: 4.2%`, `BR-010: 3.2%`, `BR-015: 3.8%`), and remaining 9 branches in `9.4%–11.8%` (`BR-001: 11.4%`, `BR-002: 11.8%`, `BR-006: 10.8%`, `BR-007: 10.8%`, `BR-008: 11.0%`, `BR-011: 9.6%`, `BR-012: 10.6%`, `BR-013: 9.4%`, `BR-014: 10.0%`).
- **Dead stock excess subset**: `deadStockValue` is summed on `position.surplus * product.cost` strictly for `OVERSTOCK` positions with `velocity < DEAD_VELOCITY_PER_DAY` (`1 / 7` ~ `0.1429/day`, `< 1 unit/week`), guaranteeing `deadStockValue <= cashReleasable` across network, cluster, and branch views.
- **Forward stock projection (`ProductPage`, UI-only read-model derivation)**: For horizon `H = max(21, 2 * leadTimeDays)` days (`t = 0 .. H`), baseline stock follows `S_base(t) = max(0, (onHand - reserved) - velocity * t)`, with projected stockout day `t_stockout = ceil((onHand - reserved) / velocity)` when within `H`. Planned stock follows `S_plan(t) = max(0, (onHand - reserved) + I(t >= 1) * inTransit + I(t >= t_arrival) * Q_rec - v_plan * t)` where `t_arrival = leadTimeDays` (`REORDER`), `min(2, H)` (`TRANSFER`), or `0` (`MARKDOWN`, accelerating clearance velocity by `1.5x`), bounded visually by the horizontal `reorderPoint` threshold and `[D+0, D+leadTimeDays]` shaded lead-time window.

## Known limitations

- Normal demand is a poor fit for intermittent SKUs. A zero-inflated or Croston estimate would change who looks "dead."
- Branches are independent except for the explicit transfer. A promotion in one city does not move the prior of another.
- Transfer cost uses pairwise Haversine distance (`km`) plus fixed dispatch and per-unit handling, though it does not model truck capacity limits or multi-stop milk runs.
- Greedy matching is not a proven optimum. A later pair can be better once an earlier pair is fixed, and we do not search that.
- The morning plan's base recommendations and EWMA demand are computed once per `dataVersion` (`this.analysis` is immutable). Order intent states (`SUGGESTED`, `OPEN_REQUEST`, `AWAITING_DONOR`) never touch `committedDeltas`; only moving into `COMMITTED` writes `donor.reserved += qty` and `receiver.inTransit += qty` (blocking donor over-allocation with `409 Conflict`), while `RECEIVED` clears `receiver.inTransit -= qty` and keeps `donor.reserved` until the next sales/catalog refresh. Alongside post-plan `LOGGED_ADJUSTMENT` alert overlays, these `committedDeltas` are replayed at startup without bumping `dataVersion` or rewriting `plan_cache`.
- Actions under `BD 9.500` net benefit or under the minimum `5`-unit transfer quantity (`isMaterialRecommendation`) are hidden by the service. They are still produced by the engine.

## Governed replenishment workflow

Recommendation decisions, manual manager stock requests, and escalated floor stock alerts flow through one unified `ReplenishmentOrder` (`ENGINE`, `MANAGER_REQUEST`, or `ALERT_ESCALATION`) and immutable `OrderEvent` pipeline (`ADR-016`):

- **Lazy materialization**: Engine recommendations start virtual (`SUGGESTED`, `isVirtual: true`) with no database write until the first human action materializes them in `replenishment_orders` under their deterministic recommendation ID; manual and alert-escalated orders use UUIDs (`ord_<uuid>`). Existing legacy `actions`/`audits` are migrated idempotently at startup.
- **Two-party cross-cluster handshake & editable commit quantities**: Intra-cluster transfers (both branches in the same manager cluster) and Admin actions may commit directly, whereas cross-cluster transfers require receiving-manager initiation (`REQUEST_TRANSFER` -> `AWAITING_DONOR`), sending-manager review in *Requests to Fulfil* (live available surplus and post-release cover days), and release (`COMMIT` / *Approve* or *Send Stock* -> `COMMITTED`) or decline with required comment (`DECLINE`). Unanswered `AWAITING_DONOR` requests escalate to Admin after 24 hours (`ESCALATE`, `DONOR_TIMEOUT_24H`). Admin force-commits require a non-empty `comment`. At `COMMIT`, authorized managers and admins may adjust `approvedQty` (server-enforced bounds: `TRANSFER` `5..min(engineQty, live donor surplus)`, `REORDER` `1..2x engineQty` with comment required above `1x`, `MARKDOWN` `1..engineQty`; any edit requires `dispositionCode` in `CASE_PACK | TRUCK_CAPACITY | PROMO_HOLD | OTHER`), preserving `engineSnapshot.qty` as read-only while recording `{ engineQty, approvedQty, dispositionCode, comment }` on `OrderEvent` and recomputing net benefit via `computeActionBenefitForQuantity()`.
- **Queue lifecycle windows & reopen rules**: The queue filters by `Pending` (default), `In progress`, and `Decided` (`APPROVED_ACTIVE_DAYS = 3`, `REJECT_SNOOZE_DAYS = 3`, `REOPEN_WINDOW_HOURS = 24`, evaluated at read time against an injectable clock). Approved items leave `Pending` immediately, remain in `In progress` for 3 days (or until `RECEIVED` for governed orders), and then move to `Decided`. Declined items capture a `{ netBenefit, targetCoverDays }` snapshot with `rejectedUntil = decidedAt + 3 days` and re-enter `Pending` automatically if the snooze expires while the recommendation persists OR if net benefit worsens by `>= 50%` (unless already manually reopened); authorized managers and admins can also reopen eligible decided actions within 24 hours via `POST /api/orders/:id/reopen`.
- **Read-only engine rationale & receipt clearing**: `engineSnapshot.reasonCodes` is immutable; human justification lives exclusively in `OrderEvent.dispositionCode` and `OrderEvent.comment`. Receiving managers or store staff confirm delivery via `POST /api/orders/:id/receive` (*Mark as Received*, `COMMITTED` -> `RECEIVED`), which decrements `target.inTransit` and invalidates `scopedKpiCache` without bumping `dataVersion`.
- **Alert resolution linkage**: Staff flag floor stock alerts with optional `reportedQty`, and managers resolve them via `POST /api/stock-alerts/:id/resolve` (`CONVERTED_TO_REQUEST` atomically creating an `ALERT_ESCALATION` order, `LOGGED_ADJUSTMENT` applying a live `adjustment` overlay, `ACKNOWLEDGED`, or `DISMISSED` with required comment) (`ADR-015`).
- **Live dashboard freshness, import logs & branch governance**: All business calendar dates normalize to `Asia/Bahrain` (`UTC+3`); `GET /api/kpis/live` and `/api/kpis?meta=1` return `asOfDataDate`, `todayBahrain`, and `staleDataDays` with cache keys stamped by both `dataVersion` and `decisionVersion`. Bulk CSV uploads append to `import_log` (`GET /api/sales/imports`, role-scoped). Branch creation/editing validates Bahrain bounds (`lat 25.5..26.4`, `lng 50.3..50.9`), rejects swapped coordinates, rounds to 6 decimals, enforces unique `(name, city)` pairs (`409`), and assigns cluster membership.

## Scaling path

At about 100 times the SKU count the per-SKU loop is still the unit of work.

- Run one worker per SKU, or per SKU shard. Classification and matching do not talk across SKUs.
- Recompute a SKU when its sales or a decision for that SKU change, not the whole network on every request.
- Keep daily rollups for the charts. The engine can keep reading the compact series.
- Swap the forecaster for Holt-Winters, Croston, or a model that has enough history. `Forecaster.estimateDemand` is the seam.
- Swap the matcher for min-cost flow or a mixed-integer program when branch count makes the pair loop too coarse. `Matcher.match` is the seam.
- Store facts in a MongoDB time-series collection with a compound shard key of branch, SKU, and date. The unique index is already `(branchId, sku, date)`.
- Move the engine to its own worker when the API process should only serve the last result.

## Security and access decisions

- **Server-side RBAC, user provisioning & role hierarchy**: UI hiding is cosmetic only; all routes enforce `authenticate` and `requirePermission` in `apps/api/src/plugins/auth.ts`. `canManageRole` enforces strict hierarchy (`admin > manager > staff`), preventing self-deactivation, own-role edits, and role escalation. `/api/users` enforces strict email format validation, minimum `8`-character passwords across create/patch/reset, and at least one assigned branch for `manager` and `staff`. `sales:enter` is enforced across all `/api/sales-entries*` routes and `/api/sales/imports` (with assigned-branch / user scoping), `/api/kpis` enforces server-side branch scoping for `manager` and `staff` (`403`/`404` separation on out-of-scope branch queries), `stock:flag:decide` is restricted to `admin` and scoped `manager`, and `POST /api/stock-alerts/:id/resolve` keeps conditional atomic `PENDING` updates ensuring resolved `stock_alerts` are immutable (`409 Conflict` on repeat decision; comment required for `DISMISSED`). On `/api/orders*`, `canTransition()` enforces role and cluster ownership server-side (sending managers see *Requests to Fulfil* where their branch is the sender; out-of-scope order IDs return `404`).
- **Post-plan branch scoping**: The cached morning plan is built once per `dataVersion` and persisted in `plan_cache`. Branch scoping (`scopeBranches`, `isBranchInScope`, `isOrderInScope`) is applied at query/projection time so cached admin state never leaks across manager/staff requests. Transfers are visible if either donor or receiver branch is in scope; reorders and markdowns are scoped by target branch. Out-of-scope `/api/locations/:id/*` and `/api/orders/:id` requests return `404`.
- **Plan persistence & versioning (`data_version` + `plan_cache`)**: Every analysis-affecting write (sales entry CRUD, CSV import once per request, catalog update/archive/restore/sample-history) increments `data_version` (`_id: "current"`) and upserts the gzipped plan (`planCompressed`, keeping documents well under MongoDB's 16 MiB limit) into `plan_cache` keyed by `dataVersion`. Order lifecycle transitions (`REQUEST_TRANSFER`, `COMMIT`, `DECLINE`, `REROUTE`, `CANCEL`, `RECEIVE`, `REOPEN`) and `LOGGED_ADJUSTMENT` alert resolutions overlay onto the cached plan via `committedDeltas` and **must not** bump `dataVersion`, recompute the plan, or rewrite `plan_cache`, instead incrementing `decisionVersion` and clearing `scopedKpiCache` (which keys cached KPI summaries by both `dataVersion` and `decisionVersion`). On every plan read, `ensureFreshPlan()` checks `data_version` (and syncs orders/alerts/decisions) (`<= 3` DB ops on warm reads): if `data_version` matches the in-process `planVersion`, it serves memory with the fresh overlay; if `plan_cache` matches, it hydrates without calling `analyze()`; otherwise a single-flight refresh recomputes, persists (falling back to compute-and-serve if persistence fails), and updates memory.
- **Order & decision atomicity**: `replenishment_orders.id` and `actions.recommendationId` have unique indexes in MongoDB (with equivalent enforcement in `InMemoryRepository`). `saveOrderWithEvent` writes each updated `ReplenishmentOrder` alongside its immutable `OrderEvent` (and `resolveStockAlert` atomically resolves a `PENDING` alert + creates an `ALERT_ESCALATION` order and `CREATED` event) inside a MongoDB replica-set transaction (`session.withTransaction`), with compensating rollback when running on standalone `mongod` or `InMemoryRepository`. Legacy `saveDecisionBatch` similarly executes inside a transaction, treating `E11000` duplicate-key errors as `"already_decided"` (`POST /api/recommendations/batch/decide` with `decision: "reject"` requires a non-empty `reasonCode`, `400` otherwise).
- **Sessions, cookies, and refresh-token families**: Access tokens are short-lived JWTs; refresh tokens live in an `HttpOnly`, `SameSite=Lax` cookie (`stockflow_refresh`, `Path=/api/auth`, `Secure` in `NODE_ENV=production`) and rotate on every `/api/auth/refresh`. Tokens belong to a `familyId` (`revokedAt` tracks rotated tokens; pre-migration tokens default `familyId = token`). Replaying a rotated token revokes every active token in that family, records a `REFRESH_TOKEN_REUSE` security audit event, and returns `401`, leaving other families and other users unaffected. `logout` revokes only the current family. `/api/auth/login` is rate-limited to 5 attempts per minute (`429`).
- **Platform hardening**: `@fastify/helmet` sets security headers, Fastify enforces a `1 MiB` JSON `bodyLimit` (`413`), production `500` responses hide stack traces, `redactSecrets` strips credentials from error logs, and production CORS emits headers only when `WEB_ORIGIN` is explicitly configured.
